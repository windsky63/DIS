# 图纸标识识别系统 2.0

图纸标识识别系统是一套面向工业管道 ISO 轴测图的本地化识别、对照、编号与人工校对工具。系统以待标识设计图为工作底图，可结合已编号对照 PDF 或 PCF 数据恢复焊口及管件身份，并将自动识别结果、人工修改记录和源图纸一起保存，最终导出 CSV 或带标识 PDF。

系统适合单机或内网部署，当前不包含账号、权限和多租户模块。自动结果始终建议由工程人员复核后再用于生产。

## 一、系统功能

### 1. 工程图纸输入

- 支持上传单份待标识 PDF，也支持一次选择多份 PDF 组成任务。
- 单份 PDF 可指定分析页码范围，避免无关封面、目录等页面参与识别。
- 可不带参考资料独立分析，也可附加以下任一种参考资料：
  - 已完成编号的对照 PDF；
  - PCF 文件或服务器 PCF 文件库。
- 支持在任务开始前检查输入清单、页数和分析模式。

### 2. 焊口识别与编号

系统提供两种焊口识别模式：

- **落图模式**：面向尚未编号的设计图，识别主管上的黑色闭合焊口符号，再根据页面拓扑和已有编号规则生成编号。
- **对照模式**：面向已经存在人工标识的图纸，读取红色编号框、红色引线及其连接焊点，直接恢复已有编号。

焊口研究配置支持调整基础形状、普通/X/方括号类型开关、符号尺寸、深色阈值、主管投影容差、红框开关、编号表达式和最低置信度。

### 3. 阀门、法兰和支架识别

除焊口外，系统还支持 `V`（阀门）、`FL`（法兰）和 `SP`（支架）三类管件。

- 在 EP3D 对照图中，系统读取黑色或红色方形标识框内的原生 PDF 文字，并沿同色引线确定管件位置。
- 几何复核支持共顶点双三角阀门、带中心方向箭头的 Z 形阀门，以及法兰/支架常见的短平行线对。
- 在设计图中，阀门优先根据右侧 `ERECTION MATERIALS` 材料表识别：描述含 `GATE`、`BALL`，或同一行同时含 `LIFT CHECK` 的材料项会被视为阀门候选；系统再在图形区寻找相同数字的方形标识框，并沿引线定位。
- 设计图侧与 EP3D 侧的候选分别记录，参考图识别结果不会反向制造设计图候选。

### 4. 页面对照与跨图匹配

- 先读取标题栏中的 ISO 图号和页序身份，再建立设计页与参考页的对应关系。
- 支持同一 ISO 图号对应多张设计页或参考页，不依赖上传顺序强行一一配对。
- 页面是否可作为对照页，与页面内是否已经找到焊口/管件对象分开判断。因此，标题身份有效但暂未识别出对象的参考页仍会进入该 ISO 的候选页集合。
- 在页面集合确定后，再利用主管骨架、稳定地标、相邻关系和编号证据完成对象级匹配。
- 页面关系和对象关系会分别保留，方便定位“页面未对应”和“页面已对应但对象未匹配”这两类问题。

这套逻辑用于处理类似 `40-42-3000-26-40DSA30001-01` 的管线：系统不会因为某张参考页暂时没有识别到焊口或管件，就提前把它从页面对照候选中删除。

### 5. PCF 语义拓扑辅助

系统可按标题栏 ISO 号选择对应 PCF，并提取：

- 焊口节点及工程坐标；
- 主构件和相邻管件类型；
- 焊口之间的连通关系；
- 可用于复核 PDF 图元关系的语义约束。

PCF 用于增强身份和拓扑一致性，不会在缺少可靠图形证据时把任意边界自动提升为焊口。

### 6. 可视化核对与人工修正

前端工作区将设计图和参考图放在同一核对流程中，支持：

- 按页浏览设计图，并查看当前页可用的参考页；
- 显示焊口、阀门、法兰和支架的参考提示，点击结果定位图中对象；
- 手工新增焊口、阀门、法兰或支架；
- 拖动标识文字和锚点，调整引线连接位置；
- 直接修改编号；
- 排除误识别项、恢复已排除项或删除人工项；
- 交换两个焊口编号；
- 从选中焊口开始重新编号，或对整页重新编号；
- 撤销、重做、缩放和平移；
- 分类型设置文字、引线、边框和标识样式；
- 自动重新排布标识，尽量避开正文、管线、锚点、其他标识和引线。

### 7. 任务队列与恢复

- 分析任务可提前加入队列，后端按并发上限执行。
- 支持查看执行中、排队、已完成、失败和已取消任务。
- 支持取消、调整排队顺序、归档、取消归档和删除终态任务。
- 服务重启后可恢复已有任务记录；异常退出时遗留的执行中任务会被标记为失败，避免永久卡住。
- 对重复输入会依据任务签名提示复用既有结果或重新分析。
- 页面会显示文件级、参考资料级和页级处理进度。

### 8. 保存、导出与容灾

- 人工修改后自动保存到后端，也可手动保存。
- 可导出编号清单 CSV。
- 可导出带标识的 PDF；导出文件内嵌可编辑结果 JSON 和原始源 PDF，便于重新打开继续核对。
- 分析完成后可生成训练样本归档，用于后续规则研究。
- 浏览器 IndexedDB 保存容灾草稿；即使后端任务文件被清理，浏览器中已有的源文件和工作区仍可用于恢复。
- 恢复入口会综合检查带标识 PDF、浏览器草稿和后端近期任务。

## 二、核心工作机制

### 1. 总体处理链路

```text
待标识 PDF
   │
   ├── 页面与标题栏解析 ──> ISO 身份、页码、图形区域
   │
   ├── 图元研究 ──────────> 焊口/阀门/法兰/支架候选
   │
   ├── 参考 PDF 或 PCF ───> 页面候选、编号证据、语义拓扑
   │
   └── 拓扑匹配与编号 ────> 可人工核对的工作区结果
                                      │
                                      ├── 后端任务存档
                                      ├── 浏览器容灾草稿
                                      ├── CSV
                                      └── 带标识 PDF
```

### 2. 页面对照机制

页面对照分为两个阶段：

1. **页面身份阶段**：从标题栏提取标准化 ISO 身份，将设计页和参考页放入同一个 ISO 候选组。只要参考页标题身份有效，即使该页的对象识别结果为空，也会保留在候选组中。
2. **对象匹配阶段**：只在候选组内比较主管骨架、稳定地标、焊口相对顺序、邻接管件和编号证据，建立具体焊口或管件的匹配关系。

这种分层机制避免两个常见错误：一是用上传顺序代替真实页码；二是因为某页暂时没有对象结果，就误判该设计页不存在对照图。

当页面没有正确对应时，应依次检查：

- 设计页和参考页的标题栏 ISO 号是否能被完整提取；
- 页序后缀是否一致，是否存在一对多页关系；
- 该页是没有进入候选集合，还是已进入集合但对象匹配数为零；
- 标题栏是否为扫描图片而非原生 PDF 文字。

### 3. 焊口候选机制

落图模式默认以实际 PDF 图元为依据：

- 优先识别主管上的黑色圆形闭合路径，包括贝塞尔圆和高圆度密集折线路径；
- 完整圆形主体的物理中心必须落在工艺管线上，只有箭头尖端投影到主管不视为焊口；
- 六边形等低边数近似圆以及非圆形复合恢复属于补充规则，默认关闭；
- 普通管件边界、共线管段间隙、横穿主管的短线和支管根部，不能仅凭拓扑或参考编号自动提升为焊口；
- `F`、`FS` 等前缀只是参考身份的一部分，不代表 PDF 图元类型；
- 是否为视觉虚线依据实际描边数组判断，不根据编号前缀猜测。

对照模式要求编号文字框和相连引线同时成立，并保留可识别编号及对应视觉虚线焊口。

### 4. 管件候选机制

EP3D 管件以“标识框 + 文字 + 引线”为身份与位置主证据，局部几何只用于复核和细分。结果写入分析 JSON 的 `ep3dComponentInventory`。

设计图阀门则以材料表语义和图形区同号标识框共同确认。设计侧和参考侧保持证据隔离，避免参考图中的对象数量直接改变设计图候选数量。

### 5. 拓扑匹配与编号机制

页面身份建立后，系统在同一候选组内构建图形关系，综合考虑：

- 主管骨架及分支结构；
- 焊口沿管线的相对次序；
- 阀门、法兰、支架等稳定地标；
- 对象之间的邻接和距离关系；
- 参考编号或 PCF 语义证据。

编号优先复用高可信的对照身份；缺少直接身份时，再依据页内拓扑和编号规则生成建议编号。参考数量只用于审计，不会通过任意图元或未匹配边界强行补足数量。

### 6. 人工编辑与持久化机制

前端操作形成工作区变更，保存时后端按页面合并修改，避免只加载当前页时覆盖其他尚未打开的页面。撤销/重做主要保存页面级编辑快照，不重复复制整套大型 PDF 文件。

带标识 PDF 同时保存可视化标记和可编辑数据；浏览器草稿则保留独立容灾副本，两者与后端任务记录共同组成三条恢复路径。

### 7. 大图纸加载与懒加载机制

大图纸恢复时的卡顿主要来自以下几类同步工作叠加：完整解析 JSON 反序列化、所有页面几何一次性进入响应式状态、多个 PDF Blob 同时读取，以及参考 PDF 和页面位图集中渲染。

当前采用分层懒加载：

- 后端首次恢复只返回当前页完整数据和其他页面的轻量布局，需要时再通过页面详情接口加载；
- 参考 PDF 不在进入工作区时全部打开，只在当前页需要时加载；
- 已打开的参考文档使用有限缓存，默认最多保留 5 份；
- 页面位图按设备能力和性能设置控制缓存；
- 浏览器草稿列表只读取摘要，不扫描每个草稿的全部文件和页面；
- 恢复草稿时先加载当前页，翻页后再读取对应页面分片；
- 首屏完成后，以低并发在后台补充必要的参考文件。

这会降低首次进入工作区的主线程压力和内存峰值。首次打开尚未缓存的页面仍可能出现短暂加载提示，这是懒加载的正常行为。

### 8. 浏览器草稿 v2 机制

浏览器草稿使用 IndexedDB 分层存储：

- `draftMetadata`：草稿名称、更新时间、页数等轻量摘要；
- `workspaceManifests`：工作区结构及文件引用；
- `workspacePages`：按工程和页码拆分的解析结果；
- `workspaceFiles`：主图、参考图和 PCF 的 Blob 文件仓库。

文件按照内容指纹去重。同一份 PDF 被多个草稿或清单引用时，只保存一份 Blob，工作区保存引用关系。新草稿使用跨仓库事务一次提交，防止写入中断后暴露半成品；旧版 `drafts` 数据继续兼容读取。

浏览器草稿的设计目标是容灾，因此不会因为后端已有同名文件就省略浏览器文件副本。优化重点放在去重、分片、懒加载和渲染调度，而不是削弱恢复能力。

## 三、推荐使用流程

1. 选择落图模式或对照模式。
2. 上传待标识 PDF；单文件任务可设置分析页码范围。
3. 根据工程资料选择对照 PDF 或 PCF；没有参考资料时可直接分析。
4. 提交任务并在任务队列中查看文件、页面和参考资料处理进度。
5. 进入工作区，先检查页面对照关系，再核对焊口和管件对象。
6. 使用排除、恢复、手工新增、拖动、改号或重新编号修正结果。
7. 保存核对结果，导出 CSV 和带标识 PDF。
8. 工程结束后按数据管理要求归档或删除后端任务及浏览器草稿。

仅上传待标识 PDF 时也能执行图元扫描，但缺少独立参考拓扑，结果应重点人工核对。

## 四、输入、结果与目录

### 主要输入

| 输入 | 是否必需 | 用途 |
| --- | --- | --- |
| 待标识 ISO PDF | 是 | 页面解析、图元识别和标识底图 |

### 主要输出

| 输出 | 内容 |

| 带标识 PDF | 原图、可视化标识和内嵌可编辑数据 |


## 五、技术架构

- 前端：Vue 3 + Vite
- 后端：Python 标准库 HTTP API
- PDF 与图元处理：PyMuPDF
- 研究引擎：`pdf_vectors`、`dual_pdf_topology`、`idf_topology`
- 本地容灾：浏览器 IndexedDB

当前程序定位为本机单用户工程工具，没有账号、权限、ORM 或后台管理需求，因此未采用 Django。轻量 API 便于本地部署、问题定位和代码审计。

## 六、本地启动

建议使用 Python 3.14 和 Node.js 22.13–24.x。前端和 Python 依赖均使用精确版本。

前端终端：

```powershell
cd frontend
npm install
npm run dev
```

后端终端：

```powershell
python backend/server.py
```

浏览器打开 `http://127.0.0.1:3004`。

首次安装依赖后，也可以双击 `启动系统.bat`。BAT 会保留可见的服务控制台并显示 Python、Vue 日志；使用期间请保持窗口开启。关闭窗口时，Windows 进程监护会同时结束前端、后端及其子进程。启动前会检查 `3004` 和 `8768` 端口，避免误连旧服务。

## 七、操作教程与内置示例

- 新用户首次打开系统会自动进入分步教程，之后可通过 Header 右上角的指南针按钮再次打开。
- 教程模式自动载入 000207 示例 PDF 和预解析结果，不重新执行图元解析。
- 教程源资源位于 `backend/tutorial/000207.pdf` 和 `backend/tutorial/result.json`。
- `data/jobs` 中只创建可编辑会话副本，清理任务目录不会影响教程源文件。

## 八、Docker 部署

项目提供多阶段 `Dockerfile`：Node.js 24 阶段构建 Vue 前端，Python 3.14 运行阶段同时托管 API 和前端静态文件。容器以非 root 用户运行，任务文件与审计日志保存在独立 Docker 卷中。

在项目根目录执行：

```bash
cp .env.example .env
docker compose build drawing-mark-recognition
docker compose up -d --force-recreate drawing-mark-recognition
docker compose logs -f drawing-mark-recognition
```

浏览器打开 `http://127.0.0.1:8768`。查看容器和健康状态：

```bash
docker compose ps
curl http://127.0.0.1:8768/api/health
```

健康接口中的 `version` 应为 `2.0.3`，`buildId` 应与 `.env` 中的本次部署值一致。生产入口 `index.html` 禁止浏览器缓存，带哈希的静态资源使用长期缓存，以避免浏览器继续显示旧入口页。

停止服务：

```powershell
docker compose down
```

`docker compose down` 不会删除 `drawing-mark-recognition-data` 数据卷；只有明确执行 `docker compose down -v` 才会删除历史任务与审计数据。

默认映射宿主机端口 `8768`。如端口被占用，可在启动前设置：

```powershell
$env:DRAWING_MARK_RECOGNITION_PORT = '8877'
docker compose up -d
```

此时访问 `http://127.0.0.1:8877`。

也可以不使用 Compose：

```powershell
docker build -t drawing-mark-recognition:latest .
docker run -d --name drawing-mark-recognition -p 8768:8768 -v drawing-mark-recognition-data:/app/data --restart unless-stopped drawing-mark-recognition:latest
```

### 基础镜像拉取 403

若错误发生在 `FROM node:24-bookworm-slim` 或 `FROM python:3.14-slim-bookworm`，说明请求尚未进入本项目，与 npm、pip 依赖无关。先分别诊断：

```bash
docker pull node:24-bookworm-slim
docker pull python:3.14-slim-bookworm
docker login
```

403 通常表示出口网络、代理、Docker Hub 账号或组织策略拒绝了认证或镜像清单请求。官方拉取配额超限通常返回 429。登录后仍为 403 时，应检查服务器能否访问 `auth.docker.io` 和 `registry-1.docker.io`，或配置可信的 registry mirror。

项目允许替换基础镜像地址，无需修改 Dockerfile：

```bash
export DRAWING_MARK_RECOGNITION_NODE_IMAGE=registry.example.com/library/node:24-bookworm-slim
export DRAWING_MARK_RECOGNITION_PYTHON_IMAGE=registry.example.com/library/python:3.14-slim-bookworm
docker compose build drawing-mark-recognition
```

服务器完全无法访问 Docker Hub 时，可在联网机器执行 `docker pull` 和 `docker save`，将归档传到服务器后用 `docker load` 导入，再执行普通构建。不要在 403 环境中使用 `--pull`。

## 九、数据、备份与安全

每次识别任务保存在 `data/jobs/<任务编号>`，包括原始上传、识别 JSON、页面预览和导出的标识 PDF。该目录默认不纳入版本控制。

- 已完成、失败或取消的任务默认保留 90 天，超期后在服务启动时清理。
- 审计日志默认达到 10 MB 后轮转，保留 5 份历史文件。
- 浏览器草稿包含工程 PDF/PCF 副本；文件敏感时，请在系统草稿管理中及时删除。
- `data/audit`、`data/jobs` 和 `backups` 均被 Git 忽略，避免工程文件名、图纸和本地备份误入代码仓库。发布源码包不包含这些运行数据。
- 当前系统没有用户鉴权，不应直接暴露到不可信公网；远程部署应在外层增加访问控制、TLS 和网络隔离。

## 十、PCF 解析器配置

系统自带内置 PCF 语义拓扑解析器。若需使用完整的 `idf-pipe-viewer` 解析器，可设置：

```powershell
$env:PCF_REFERENCE_PARSER = 'D:\tools\idf-pipe-viewer\scripts\parse_pcf_to_json.py'
$env:IDF_REFERENCE_PARSER = 'D:\tools\idf-pipe-viewer\scripts\parse_idf_to_json.py'
```

也可以把解析器放在 `backend/vendor/idf-pipe-viewer/scripts`。解析器不可用时，结果 JSON 的 `pcf.degraded` 为 `true`，前端会显示警告。

Docker 使用外部 PCF 解析器或 PCF 文件库时，可在 `compose.yaml` 中增加只读目录挂载，并设置 `PCF_REFERENCE_PARSER`、`IDF_REFERENCE_PARSER`。

## 十三、使用边界与问题排查

- 扫描版 PDF 缺少原生文字和矢量图元，标题栏、编号框及引线识别能力会明显下降；当前核心流程更适合矢量 PDF。
- 无参考资料时，系统只能依据设计图自身的视觉和拓扑证据生成候选，必须加强人工复核。
- 自动识别数量与参考数量不一致时，应核查证据来源，不应以参考数量为目标强行补齐。
- 出现“设计页无对照图”时，先检查页面身份候选；出现“有对照页但无对象”时，再检查对象识别和拓扑匹配。
- 大图纸第一次翻到未缓存页面时会按需加载；若持续卡顿，应结合文件大小、页数、参考文件数量、浏览器内存及控制台错误进一步定位。
